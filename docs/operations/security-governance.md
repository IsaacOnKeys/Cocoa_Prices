# Essential security and governance

Owner: Isaac Haire. Scope: this CV project's GCP application, deployment inputs and retained operational evidence. This records both controls and exceptions; it is not a claim that the project has no vulnerabilities.

## Runtime and operator responsibilities

Daily producers use the shared `analytics-producer` runtime identity: publish only to the three fact topics, create/read only daily-input and acquisition-coverage evidence prefixes, update only the acquisition-coverage state prefix, and access only the EIA secret. Sharing one identity across the three producers is intentional for this small pipeline. It has no project-level build, compute administration or BigQuery role. The legacy compute identity remains the build/optional manually run backfill identity; Eventarc uses its existing scoped invocation bindings. It is not the daily producer runtime.

Airflow uses `airflow-orchestrator`; staging and watchdog keep their separate existing identities. Airflow publishes only to its two trigger topics and invokes the explicitly granted producer services. Dataset-level editor grants, the project job-user grant, and the scoped raw/temp/backup bucket grants cover its warehouse and receipt duties. Secret access is per secret: EIA for producers, Fernet for Airflow. App Engine's unused identity receives no project-wide secret access. Operator privileges are separate from runtime privileges; no downloaded service-account key is introduced.

The cleanup removes 18 unnecessary project-wide bindings and the former build identity's EIA-secret grant. A negative permission probe additionally found six legacy, unmanaged Airflow publisher/viewer grants on the three fact topics; those were removed using their exact policy etags while preserving other members. The old `api-fetcher` identity retains its resource-scoped manual-publisher grants and has no user-managed key; it is not used by the serving functions. Topic-policy preimages and removal receipts are retained privately. These one-time removals are not implied by a Terraform no-change plan: recheck actual topic policies when auditing unexpected publish rights.

The initial native review found zero user-managed keys on the six existing runtime/build/scheduler identities. The new producer identity also uses managed credentials. Deployment uses the operator's short-lived CLI tokens; the runtime uses metadata credentials. Permission validation can use a narrowly scoped expiring impersonation grant, removed after the probe; minted tokens remain valid until their short expiry. Never put tokens, key values, private state or environment dumps in logs, Git or release bundles.

These controls follow Google's [secret-level least-privilege guidance](https://docs.cloud.google.com/secret-manager/docs/best-practices). Do not give a daily producer its build identity's roles to fix a missing permission; add only the required resource/prefix grant and verify the intended denial boundaries.

## Network and invocation

Cloud Run IAM is enabled for all five serving functions, and the native review found no allUsers/allAuthenticatedUsers service bindings. ALLOW_ALL ingress alone does not establish public invocation; inspect IAM and the invoker-check setting together. Existing anonymous-denial receipts are in the ingestion/watchdog runbooks. Do not probe an upstream producer with an unauthenticated request that could trigger acquisition if access were accidentally public.

Default VPC SSH/RDP allow rules apply more broadly than the original operator/IAP rules. The VM-specific priority-1100 admin deny takes precedence over those priority-65534 defaults, while the priority-1000 operator/IAP SSH allows remain usable. It targets only the Airflow VM's tag, leaving other workloads alone. Port 8080 now permits IAP sources only; the adopted `allow-airflow-ui-myip` name remains but its old public-IP source has been retired. Use IAP to localhost rather than sending Airflow credentials over public HTTP:

```text
gcloud compute start-iap-tunnel airflow-vm 8080 --local-host-port=localhost:18080 --zone=europe-west3-c --project=cocoa-prices-430315
```

Open `http://localhost:18080` while the VM is running. Application health, firewall rule evaluation, successful IAP tunneling and browser acceptance are distinct checks; do not claim rendered UI access from a stopped-VM metadata check.

## Credentials and retired-provider question

EIA keys are created/revoked in the owner's EIA account, then new values are added directly to Secret Manager. Google-managed encryption is retained; Terraform manages secret containers and resource-scoped access, not secret values/versions. Test a new version in isolation before moving the active alias/selector; disable the superseded version after validation. Review ownership quarterly and rotate after a confirmed disclosure, suspected compromise or ownership change. Do not post the value into chat, a command argument, a ticket or a repository file.

Fernet rotation needs the runtime backup runbook: preserve every numeric key version still referenced by retained backups and re-encrypt metadata using Airflow's supported rotation process before retiring old versions. Never replace Fernet as though it were a disposable API key. Keep the matching key-version reference with the encrypted backup receipt, never the key value beside the archive.

The retired FRED secret is not required by any serving producer. A bounded native query inspected all 17 matching old-producer `api_key` log entries from 2026-10-01 through 2026-10-31 and found no credential-shaped query-string matches. Raw entries and secret values were neither printed nor retained by the audit. This does not prove that older, expired or differently formatted logs never contained a credential. No disclosure was confirmed by that check. Disabling the retired Secret Manager version prevents accidental application reuse; it does not revoke the credential in the provider's account. Any confirmed exposure requires owner-side provider revocation, not merely log deletion or Secret Manager disablement.

## Audit evidence, residency and source use

Observed Cloud Logging retention is 30 days for `_Default` and locked 400 days for `_Required`. Secret Manager DATA_READ audit logging is enabled specifically for secret access; do not enable every service's Data Access category indiscriminately. Google documents [Secret Manager audit categories](https://docs.cloud.google.com/secret-manager/docs/audit-logging) and the [Data Access defaults](https://docs.cloud.google.com/logging/docs/audit/best-practices). The operator must have the appropriate private-log access for Data Access evidence. Runtime identities do not need blanket private-audit-log access. Do not export a second full audit stream or create a new logging service for this CV project.

The workload's VM, BigQuery datasets and application storage are in europe-west3. Secret Manager uses automatic replication and the reviewed logging buckets are global; this is not an EU-only residency guarantee. Operational IAM, email/IP and audit metadata also exist. Review any new residency or personal-data requirement before claiming compliance. Source-use decisions remain in the EIA migration and source contracts: preserve provenance, explicit missing dates and unknown historical publication times. Retired-provider rollback instructions do not authorize renewed supplier use or model training contrary to its terms.

## Scanning, patch review and explicit exceptions

`Security review` scans only this repository's committed files through a clean Git archive, not local generated/private directories. Gitleaks is pinned by official image digest and runs with redacted output and no container network. Dependency auditing uses pip-audit 2.10.1 against each resolved Python 3.11 graph; it does not install or resolve new runtime packages. It runs manually and weekly on Monday; ordinary source changes receive the small secret scan. A failed advisory job stays visible: no blanket ignore or success override hides known vulnerabilities. Hosted execution and GitHub notification delivery are not established by local validation.

Review new findings weekly, confirmed credential leakage immediately, and the runtime patch backlog at least monthly. Separate actual affected behavior and exposure from scanner counts; advisories can repeat identifiers or describe behavior this project does not invoke. Reproduce candidate fixes in the affected isolated component, retain old artifacts, then use the controlled deployment procedure. Do not mutate the active environment with pip-audit's automatic fix option.

**Owner-approved exception, 2026-10-31:** keep Airflow 2.10.2 temporarily for this CV demo. Airflow 2 is past its support end date ([Apache's current statement](https://airflow.apache.org/blog/common-ai-provider-1.0/)); the captured graph audit returned 448 advisory entries across 60 packages, including 61 entries for Airflow. These are scanner records, including duplicate IDs, not 448 proven independent exploits. The owner explicitly chose an exception over an Airflow 3 metadata/runtime migration. Review by 2026-11-30, before expanding audience or exposure, and immediately after a relevant high-impact advisory. The stopped-outside-window VM, restricted UI, private invocation and scoped IAM reduce exposure; they do not patch the vulnerable packages. Do not describe this deployment as fully patched or security-hardened for a real production workload.

The optional Beam graph returned nine advisory entries across httplib2 0.22.0, protobuf 4.25.3 and pyarrow 16.1.0. Its current Beam constraints prevent some fixed versions, so a supported Beam/dependency refresh is a separate reviewed patch task. Backfills remain manual and limited to verified, held, size-bounded CSV/JSON inputs; do not accept arbitrary Parquet/binary files or unreviewed pipelines. This is recorded residual patch debt, not suppressed scanner output. All five newly constrained function graphs returned no known advisories at the time of this review. Those constraint-bearing artifacts were then promoted from the verified item 32 bundle, with matching serving archive hashes; the snapshot does not establish future absence of advisories or audit Google's managed build/OS packages. Python AST and Avro schema comparisons against the previous serving code confirmed no behavior/contract change. Each daily producer is capped at one instance, with zero minimum instances, to bound cost exposure.
