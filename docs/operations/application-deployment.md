# Reproducible application deployment and rollback

Checklist item 32 uses an explicit Git-pinned release bundle and the existing component deployment/recovery paths. Promotion remains an operator-reviewed procedure; packaging never applies infrastructure, SQL or functions, and does not access credentials or GCP. This avoids an unattended deployment service for a small CV project.

## Build and verify an identified candidate

```powershell
.build/python311-dev/Scripts/python.exe scripts/deploy/package_release.py --revision HEAD --namespace application_validation_20261031_1234abcd --output .build/application-release-001
.build/python311-dev/Scripts/python.exe scripts/deploy/package_release.py --verify .build/application-release-001
```

Use a new output directory and a unique isolated namespace for each candidate. The builder reads committed Git blobs, not mutable working-tree files. Its manifest records the full Git commit, builder SHA, Python version, namespace map and SHA256 of every emitted file. `source.zip` includes only tracked application/build/schema/SQL/operations/IaC definition and runbook inputs, filtered by explicit paths and file types. It excludes private tfvars, state, `.env`, credential JSON, generated files and untracked inputs. Five deterministic function ZIPs include their resolved dependency constraints. Rendered SQL targets the explicit isolated namespaces; production namespaces are refused by this builder.

Save the printed manifest SHA in the private deployment receipt, outside the candidate directory, and compare it before `--verify`. File checksums detect changed artifacts; they do not authenticate a replaced manifest. Verify before extraction, again after transfer and before promotion. Do not build from a dirty checkout expecting uncommitted fixes to appear: commit the intended changes and build that exact commit. Never overlay candidate source into an existing runtime directory.

## Ownership and bootstrap requirements

| Component | Desired-state owner | Promotion / recovery |
| --- | --- | --- |
| Producer source and configuration | Terraform `functions.tf`, checksum/generation-pinned GCS source | Upload the candidate's exact ZIP as a new immutable object, record generation/SHA, update the matching source selector, review the saved Terraform plan and apply it. Restore the previous object/generation through the same owner on failure. |
| Ingestion / watchdog source | Terraform `ingestion.tf` / `operational_alerts.tf` | Same source-pin process; preserve routes, private invocation and existing identities. Never let a stale seed artifact replace tested code. |
| Topics, subscriptions, IAM, datasets, VM, alerts and retention | Terraform main/bootstrap state | Existing remote state, project APIs and operator authorization are prerequisites. Review both plans where relevant; prevent_destroy is a guard, not a substitute for review. Source ZIPs are application inputs to Terraform. |
| Table definitions, routines and serving views | Reviewed SQL migrations and renderer | Apply required additive migrations before dependent routines/views. Inspect INFORMATION_SCHEMA for actual compatibility; the SQL source is not a license to drop/recreate accepted tables. Terraform owns dataset shells, not these application objects. |
| DAG, runtime helpers and systemd units | VM application release directories and installed configuration | Record exact installed hashes, unit paths, UID/GID/modes, resolved Compose images and non-secret settings; use bounded maintenance and encrypted runtime backup. Restore exact preimages and compatible routine pin on failure. |
| Airflow/Beam images | Digest-pinned Dockerfiles and Python constraints | Build once from candidate source, record immutable image IDs and pip check/component receipts. Promote image selectors only after validation; retain the last accepted images. Dataflow worker execution remains a separately reviewed optional backfill path. |
| Secrets, Airflow Variables/connections, metadata and source archives | Secret Manager / encrypted runtime backup / retained warehouse/raw evidence | Supply references and restore compatible metadata; never put secret values into this bundle, Git, command output or Terraform plan attachments. |

Fresh-environment bootstrap requires the separately managed GCP infrastructure, authorized operator, Docker, Python 3.11, Google CLI, existing Secret Manager versions and non-secret routing/configuration. The sanitized Compose file deliberately requires external secret values and does not recreate historical metadata, credentials or source archives. Restore the existing runtime with the [backup runbook](runtime-backup-restore.md), rather than running `airflow-init` against its metadata or resetting a volume. The old `restart_with_secrets.sh` is historical setup material; current installed startup is `airflow_runtime.py` under the bounded systemd service.

Three Terraform ignore boundaries need explicit live inspection: dataset `access` retains externally managed human/default groups while application grants are additive; VM `metadata` retains the deployed bootstrap/startup mapping; Eventarc subscription `push_config` and `labels` remain Eventarc-owned. Ignored fields can drift without a plan reporting them. Function source is **not** ignored: any new build or runtime change must retain/update the exact reviewed source generation. Inspect actual trigger endpoints and identities, not just Git or a clean plan.

## Controlled promotion

1. **Preflight and recovery receipt.** Record candidate manifest SHA; current function source generations/revisions; routine bodies/hashes; required table schemas and active analytics release; VM installed paths, DAG hash, image IDs, Compose non-secret configuration, unit definitions, original power/pause state and in-flight work. Keep SQL/VM preimages and an encrypted matching runtime backup. Avoid logging secret-bearing descriptions/Compose output. Stop if concurrent runs or an incompatible schema/key/routine pin make rollback unsafe.
2. **Isolation.** Verify/extract `source.zip` into a fresh directory; build with the bundled Dockerfiles, constraints and Docker ignore files. Run the changed component checks in [integration testing](integration-testing.md), using no production credentials for local execution. For IO or publication changes, use the namespace-guarded GCP probes already described there; they use their own receipts and namespaces, so do not execute the generated isolated SQL against production or substitute arbitrary destinations. Their paid ML/SQL paths are optional when unchanged and must fit the existing cost envelope.
3. **Compatibility and reviewed plan.** Review the bundle's migrations explicitly; it contains historical SQL, not an automatic migration order. For the current analytics delivery path the additive ledger migrations are 019, 020, 024 and 029, alongside the existing staging/base schema. Existing deployments already have them. The legacy bootstrap is for a specifically verified first cutover, not every deploy. Render the intended production routine/views with the reviewed identifiers only after isolation passes. Derive the routine-body SHA from the actual stored procedure after installation and pin the matching DAG; a mismatch must keep publication blocked. Do not make an old DAG accept arbitrary routine code.
4. **Promote only changed components.** For functions upload immutable ZIPs and review/apply exact Terraform source pins; retain old generations. For VM/SQL changes pause an idle DAG and follow the existing bounded runtime/atomic-release procedures, keeping metadata and serving data intact. Do not run init, delete volumes, start legacy consumers, invoke suppliers or train a model just because an artifact changed. Do not use the bundle's Terraform configuration as an isolated-state bootstrap without reviewing its production backend/project selectors.
5. **Smoke and reconcile.** Confirm private access, intended trigger/routes, source archive member hashes, matching DAG/routine pin, component import/readiness and the relevant isolated IO checks. A controlled daily run is needed for changed daily behavior; reuse existing receipts for unchanged behavior. Record success, artifact generations/image IDs, exact changed components and any remaining limitations. Restore original pause/power state outside the operating window. Take a new matching runtime backup if installed runtime/routine compatibility changed.
6. **Rollback on a failed gate.** Stop new submissions and reconcile in-flight deliveries/jobs first. Restore previous function object/generation pins with Terraform; restore VM preimages/image selectors with their exact ownership and key-version references; restore a compatible routine/DAG pair. Additive columns/ledgers normally remain: never roll them back by dropping accepted evidence. If a bad analytics release was actually published, use `rollback_release.py` with retained target, expected-current release, incident key and reason; application code rollback alone does not restore data. Recheck hashes/readiness and affected serving outputs, record the incident and return to the bounded schedule.

Use short-lived CLI user tokens or approved impersonation for operator work and the existing VM identity for runtime operations. No new downloaded service-account key or credentialed PR workflow is needed. Do not silently change operator identities or IAM to make a deployment pass.
